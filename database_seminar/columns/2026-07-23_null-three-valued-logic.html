NULLの扱いは実装依存？——SQLの「第3の真偽値」UNKNOWN

2026-07-23

エラーにならないのに，1行も返ってこない

次のSQL，何が返ってくるでしょうか．上司がいない（上司IDがNULLの）社員を探したいつもりです．

SELECT * FROM 社員 WHERE 上司ID = NULL;

答えは「常に0行」です．エラーにはなりません．どんなにNULLの行があっても，1行も返ってきません．正しくは IS NULL を使います．

SELECT * FROM 社員 WHERE 上司ID IS NULL;

「= NULL と書いたら文法エラーにしてくれればいいのに」と思いますよね．なぜエラーにならず，なぜ0行なのか．その鍵が今回の主役，UNKNOWN です．

SQLの真偽値は3つある

多くのプログラミング言語では，条件式の結果はTRUEかFALSEの2択です．しかしSQLでは，真偽値は3つあります．

  • TRUE（真）
  • FALSE（偽）
  • UNKNOWN（不明）

これはSQL標準（最初期の規格から）で決められた仕様で，「3値論理」と呼ばれます．ルールはシンプルです．

  • NULLが絡む比較の結果は，すべてUNKNOWNになる

1 = NULL も 1 <> NULL も，さらには NULL = NULL すらUNKNOWNです．NULLは「値がない・不明」を表す印なので，「不明なもの同士が等しいかどうかは，不明」というわけです．

そして，もうひとつの重要ルールがこれです．

  • WHERE句はTRUEの行だけを残す（FALSEもUNKNOWNも捨てられる）

冒頭の = NULL が0行になる理由がこれで説明できます．上司ID = NULL はどの行でもUNKNOWNになり，UNKNOWNの行はWHEREで全部捨てられる．だからエラーではなく「静かに0行」なのです．エラーで止まってくれるバグより，動いているように見えるバグのほうがタチが悪い——というのはプログラミング全般の教訓ですが，= NULL はその典型例です．

AND・ORにもUNKNOWNは伝播する

UNKNOWNは論理演算にも顔を出します．「UNKNOWNは，あとでTRUEにもFALSEにもなり得る保留値」と考えると，次の結果が導けます．

  • FALSE AND UNKNOWN → FALSE（片方がFALSEなら，もう片方が何であれ結果は確定）
  • TRUE AND UNKNOWN → UNKNOWN（もう片方次第なので保留）
  • TRUE OR UNKNOWN → TRUE（片方がTRUEなら確定）
  • FALSE OR UNKNOWN → UNKNOWN
  • NOT UNKNOWN → UNKNOWN（不明の否定は，やっぱり不明）

最後の NOT UNKNOWN → UNKNOWN が，次の罠につながります．

NOT INの罠：リストにNULLが1つあると必ず0件

第12回で学んだ副問合せと組み合わせた，実務でも有名な罠を紹介します．社員テーブルで「部下を持たない社員」（＝誰の上司でもない社員）を数えてみます．

SELECT COUNT(*) FROM 社員
  WHERE 社員ID NOT IN (SELECT 上司ID FROM 社員);

一見正しそうですが，このクエリは上司IDにNULLが1件でもあると必ず0件を返します．部下を持たない社員が実際には何人いても，です．

種明かしをすると，x NOT IN (a, b, NULL) は次の式と等価です．

x <> a AND x <> b AND x <> NULL

最後の x <> NULL は常にUNKNOWN．すると全体は「TRUE AND TRUE AND UNKNOWN」のような形になり，決してTRUEになりません（FALSEかUNKNOWNのみ）．WHEREはTRUEしか残さないので，結果は必ず0件です．

対策は，副問合せの結果からNULLを除外しておくことです．

SELECT COUNT(*) FROM 社員
  WHERE 社員ID NOT IN (
    SELECT 上司ID FROM 社員 WHERE 上司ID IS NOT NULL
  );

怖いのは，このバグが「0件」というもっともらしい結果を返すことです．「該当なし，よかった」と誤読しても，どこからもエラーは出ません．NOT INと副問合せを組み合わせるときは，NULLの除外を習慣にするのがおすすめです．

どこまでが標準で，どこからが実装依存か

「NULLの挙動は処理系依存なんでしょ？」という印象を持っている人は少なくありません（私も長らくそう思っていました）．実はNULLまわりは「評価のコアはSQL標準で一枚岩，周辺の挙動は実装依存」という混在地帯で，この印象は半分だけ正しいのです．

標準で決まっていて，どの処理系でも同じ

  • 3値論理（NULLとの比較はUNKNOWN，WHEREはTRUEのみ残す）——今回の話はすべてここ
  • 集約関数（COUNT(列名)，SUMなど）はNULLを無視する
  • GROUP BYやDISTINCTでは，NULL同士は同じグループとして扱われる

実装依存，または処理系によって差がある

  • ORDER BYでNULLが先頭に来るか末尾に来るか．標準は決めておらず，SQLiteは昇順で先頭，PostgreSQLは昇順で末尾に来ます．第13回の資料でSQLiteとPostgreSQLの並び順の違いに注記を入れたのは，まさにこれが理由です
  • UNIQUE制約の列に複数のNULLを入れられるか（SQLiteやPostgreSQLは入れられる．入れられない処理系もある）
  • Oracleでは空文字列 '' がNULL扱いになる（移植で踏みやすい有名な仕様）

つまり「並び順や制約まわりは処理系ごとに確認が必要．でも比較と論理演算のルールを疑う必要はない」が正確な世界観です．

Colabで試してみよう

演習環境（SQLite）で，次の3つを実行してみてください．

SELECT NULL = NULL;   -- NULL（UNKNOWNの意味）が返る．TRUEではない
SELECT 1 WHERE NULL = NULL;   -- 0行．WHEREはTRUEしか残さない
SELECT 1 WHERE NULL IS NULL;  -- 1行返る．NULL判定はIS NULLで

SQLiteにはBOOLEAN型がないため，UNKNOWNは結果上NULLとして表示されます（PostgreSQLでも同様にNULLが返ります）．「真偽値が3つある」ことを一度体で覚えておくと，= NULL やNOT INの罠に，この先の実務で引っかからずに済みます．
